# 0012 · A push is not refused for what came with the base branch

**Decision.** A push of a branch the remote already has is read against what the remote has of it (`tip..head`).
Once the base branch came into the branch in between (a rebase onto it, a merge of it), the branch is also read from
where it now leaves the base branch, as the pull request shows it, and the difference from the old tip still counts
for every file the base branch's incoming commits did not touch. The base branch is read from the remote's branches
only, never a local branch the agent can move. The same care applies to the `git commit` that concludes a merge that
stopped on a conflict (read against both parents) and to a branch that follows the base branch itself.

**Why.** Reading a push only as the diff from the branch's previous remote tip refused it for someone else's change
to a test that arrived with the base: a false refusal the agent cannot fix. Keeping the old range for the other files
keeps a test the branch had already pushed and then dropped on the way.

**Alternatives.** Only the diff from the previous remote tip (the false refusals above). Only the diff from where the
branch leaves the base (it would forget what the branch changed since its last push).

**Consequences.** What the branch changed since its last push is not read in the files the base's incoming commits
touched. Where the command leaves a doubt about where the push goes, or the clone cannot name the remote's default
branch, Foreman falls back to a stricter reading. The plugin's README lists these limits.
